## C1：A Survey of AIOps in the Era of Large Language Models

- 编号：C1
- 作者 / 年份：Lingzhe Zhang 等，2025
- 来源：arXiv:2507.12472v1；J. ACM 投稿排版版，35 页
- 本地文件：`文献/03_根因分析_Agent/C1_arXiv2507.12472_AIOps_LLM_Survey.pdf`
- 一句话定位：系统梳理 LLM 如何重塑 AIOps 的数据、任务、方法和评测体系。

### 核心逻辑

这篇综述不把 LLM 看成一个单独的算法，而是把它放进 AIOps 全流程中分析：

**数据 → 任务 → 方法 → 评测。**

1. **数据层：从传统监控数据走向多源语义数据。**
   - 传统 AIOps 主要使用 metrics、logs、traces。
   - LLM 使源代码、配置文件、问答知识、事故报告等“语义丰富但结构较弱”的数据也能被利用。
   - LLM 既改进日志解析等预处理，也能直接理解非结构化文本。

2. **任务层：AIOps 被组织为三段式流程。**
   - 故障感知：预测、异常检测、故障定位。
   - 根因分析：定位故障组件、判断故障类别、生成根因报告。
   - 辅助处置：问答、处置方案、命令推荐、脚本生成、自动执行。
   - LLM 时代新增了根因报告生成、问答、命令/脚本生成和自动执行等任务，自动化程度提高，但风险同步上升。

3. **方法层：五类路线共同支撑 AIOps。**
   - 基础模型直接使用；
   - 微调或参数高效微调；
   - Embedding 表征与表征复用；
   - Prompt / In-Context Learning / CoT；
   - 知识增强，包括 RAG 和工具增强生成（TAG）。
   - 方法选择取决于数据形式、任务阶段和是否允许执行外部动作，而不是越复杂越好。

4. **评测层：从传统准确率转向生成质量、执行效果和人工评价。**
   - 根因与处置任务不能只用分类准确率，还要看正确性、有用性、引用依据、幻觉/推理错误和检索错误。
   - 脚本类任务需要看功能正确性、执行成功率和可安全执行性。
   - 开放式根因报告和处置建议普遍需要人工评价。

### 最核心的判断

**LLM 对 AIOps 的价值，不是替代原有监控与规则系统，而是增强其数据理解、跨源综合、知识检索和工具调用能力。** 好方案应当根据任务阶段选择合适方法，并在自动化收益、成本、可泛化性和安全风险之间取得平衡。

### 对本项目的用途

- 可用它给综述提供总框架：把本项目定位为“故障感知之后的根因分析 + 辅助处置”。
- 本项目主要属于 **知识增强路线**：RAG 检索规程和案例，TAG/工具调用完成三比值、产气速率等确定性计算。
- 评测不能只看“答案像不像”，还应覆盖根因正确性、证据可追溯性、处置合规性和人工可用性。
- 对油浸式变压器而言，必须限制“自动执行”等级：建议只做到根因报告和处置建议生成，高风险操作必须经过规则校验与人工复核。
- 综述引用位置：任务分类、Agent/RAG 方法选型和 LLM-AIOps 评测指标。

### 安全边界

C1 给出的是软件系统 AIOps 的通用框架，不能直接迁移为电力设备故障诊断标准。它可以提供流程与评测思路，但 DL/T 722、DL/T 572、GB 26860 等专业规则仍然是本项目的最终判据。

### 归类建议（Codex，2026-09-10）

- **只读三节**：任务三段式（故障感知 / 根因分析 / 辅助处置）、五类方法（直接使用 / 微调 / Embedding / Prompt / 知识增强）、评测指标（正确性、引用依据、幻觉、检索错误、人工评价）。
- **跳过**：论文筛选流程、逐篇文献罗列、具体案例细节。
- **引用位置**：综述总框架与评测设计；结论仍以 DL/T 722、DL/T 572、GB 26860 为准。

## C3：Exploring LLM-based Agents for Root Cause Analysis

- 编号：C3
- 作者 / 年份：Devjeet Roy 等，2024
- 来源：arXiv:2403.04123v1
- 本地文件：`文献/03_根因分析_Agent/C3_arXiv2403.04123_LLM_Agents_RCA.pdf`
- 一句话定位：把现成 ReAct Agent 用于云事故 RCA，重点做实证评估和工程案例，不是新方法论文。

### 核心逻辑

1. **问题**：已有 LLM RCA 主要处理静态事故报告，不能像人一样动态查询日志、指标、数据库或其他诊断服务，因此诊断能力受限。
2. **做法**：基于 ReAct 和 LangChain 构建 Agent，使用固定的检索/诊断工具，采用 zero-shot prompting，最多执行 20 轮 thought-action-observation 循环。
3. **评估**：在大型 IT 企业的生产事故数据上做 out-of-distribution 测试，与检索基线、CoT、IR-CoT 等方法比较，并用词汇相似度、语义相似度和人工定性编码分析结果。
4. **主要发现**：
   - ReAct 在自动指标上与强检索/推理基线接近，但定性分析显示其事实准确性更好；
   - 把事故讨论评论加入输入，并没有带来稳定、显著的 RCA 性能提升；
   - 静态数据无法体现 Agent 动态调用诊断工具的真正价值；
   - 在与 Microsoft 团队合作的案例中，接入团队实际使用的专用诊断工具后，Agent 的实用性才得到更充分体现。
5. **核心结论**：RCA Agent 的关键不只是“会推理”，而是能访问正确的专用诊断工具；仅增加历史文本或讨论内容，不足以替代真实诊断数据。

### 专业评价

- **研究定位**：这是 empirical study / case study，主要贡献是实证结果和工程经验，而不是新的算法、模型结构或复杂工作流。
- **方法贡献较弱**：核心框架沿用 ReAct、LangChain 和固定工具集，没有提出新的推理机制或知识表示方法；所谓方案更接近“标准 ReAct 工作流 + 工具接入案例”。
- **写作观感**：摘要和引言使用较多通用行业背景叙事，前半部分大量回顾已有研究；如果以“是否提出新方法”为标准，确实会显得创新度不足。
- **仍有价值的部分**：它提供了两个有用结论——讨论评论未必改善 RCA；专用工具和可交互诊断环境比单纯扩建静态语料更重要。
- **使用建议**：适合作为“已有 LLM RCA 方法局限”和“工具增强必要性”的实证引用，不宜作为核心方法创新对标。

### 对本项目的用途

- 支撑本项目“不能只做案例文档 RAG，还要提供计算与查询工具”的设计判断。
- 对本项目而言，专用工具应至少包括：DGA 注意值判断、产气速率计算、三比值编码、历史试验查询、规程条款检索和案例检索。
- 可引用其负结果说明：仅把更多事故描述或讨论文本塞给 LLM，不会自动提升根因分析质量。
- 与 C2 RCAgent 的关系：C2 展示较强工程系统设计；C3 更像用 ReAct 做验证，证明“没有合适工具和交互环境的 Agent 很难发挥优势”。

### 一句话结论

**C3 的方法创新有限，本质上是用现成 ReAct 框架做云 RCA 实证和案例研究；它的主要价值是证明专用诊断工具与实际交互环境的重要性，而不是提供可直接迁移的新架构。**

### 归类建议（Codex，2026-09-10）

- **分级：B 级·略读参引**（不进必读精读名单）。
- **理由**：方法沿用 ReAct + LangChain + 固定工具集，属 empirical study / case study；核心贡献是**负结果与工程经验**，不构成新的算法或工作流对标。
- **主题归属不变**：仍属 C 组（根因分析 / Agent），文件位置保持 `文献/03_根因分析_Agent/`。
- **引用位置**：综述「根因分析现状」中“已有 LLM RCA 方法的局限”“专用诊断工具与实际交互环境的必要性”两处；用它的负结果（补充讨论文本不提升 RCA），**不用它做方法对标**（方法对标用 C2 RCAgent）。
- **合并处理**：与 C4（Practical RCA by LLMs）同类，可合并叙述为“云 RCA 的实证与工程经验”。

## C4：Automatic Root Cause Analysis via Large Language Models for Cloud Incidents（RCACopilot）

- 编号：C4
- 作者 / 年份：Yinfang Chen 等，2024
- 来源：EuroSys '24；arXiv:2305.15778v4；DOI: 10.1145/3627703.3629553
- 本地文件：`文献/03_根因分析_Agent/C4_arXiv2305.15778_Practical_RCA_LLM.pdf`
- 一句话定位：把 OCE 预设的故障处理流程、多源诊断数据采集和 LLM 推理组合成可上线的云事故 RCA 系统。

### 核心逻辑

RCACopilot 的核心不是“让 LLM 直接读事故描述然后猜根因”，而是把 RCA 拆成一个**确定性与生成式能力结合的流水线**：

```text
事故告警
  -> 按告警类型匹配对应 incident handler
  -> 执行 handler 中的 check/query/mitigation action
  -> 采集 logs、metrics、traces 等多源诊断信息
  -> LLM 汇总诊断信息
  -> 从历史事故库检索相似事故
  -> LLM + CoT 预测根因类别并生成解释
  -> 输出根因类别、解释和必要的人工决策信息
```

具体分为两个阶段：

1. **诊断信息收集阶段**
   - 先根据 incoming incident 的告警类型匹配对应的 incident handler；
   - handler 由经验丰富的 OCE 预先定义，包含 check、query、mitigation 等 action；
   - 从不同数据源自动采集与事故相关的日志、指标、链路等信息；
   - 通过预定义 action 控制采集范围，避免把所有数据无差别塞给 LLM。

2. **LLM 根因解释与预测阶段**
   - 将多源诊断信息总结成适合 LLM 处理的上下文；
   - 从历史事故向量库中检索 K 个相似事故；
   - 使用 GPT-3.5/GPT-4 和 chain-of-thought prompting 预测根因类别；
   - 同时输出自然语言解释，必要时可揭示新的根因类别。

### 关键数据与结果

- 数据：Microsoft Transport 邮件服务一年的 **653 个真实事故**，由 OCE 人工标注根因类别；按 75%/25% 划分训练和测试。
- 模型：GPT-3.5-turbo 与 GPT-4（8K），默认采用 GPT-4。
- 主结果：Micro-F1 最高 **0.766**，Macro-F1 为 **0.533**，单次运行开销约 **4.205 秒**。
- 消融显示：多源诊断信息收集、GPT 总结、CoT prompting 都对最终效果有贡献。
- 部署：诊断信息收集组件在 Microsoft 的 30 个团队中使用超过四年；三轮实验的 Micro-F1 均保持在 0.70 以上。

### 核心价值

这篇论文最重要的并不是提出新的 LLM 模型，而是给出一个可落地的工程范式：

- **确定性流程负责“查什么、从哪里查”**；
- **多源数据负责提供证据**；
- **LLM 负责总结、关联、分类和解释**；
- **历史事故检索负责引入经验**；
- **OCE 定义的 handler 负责约束自动化边界**。

它说明，在真实工业 RCA 中，LLM 不是单独工作的“全能诊断员”，而是流程中的一个高质量解释和预测组件。

### 对本项目的用途

- 与 C2 RCAgent 相比，C4 更强调 **预定义处理流程 + 多源诊断数据 + 历史事故检索**；这比让 Agent 完全自由探索更适合本项目的高安全要求。
- 本项目可借鉴其“handler 思维”：按故障现象/告警类型预设调查路径，例如乙炔异常、总烃超注意值、局部放电特征等。
- 可采用类似结构：
  - 规则层：DL/T 722 判据、三比值编码、产气速率；
  - 数据层：油色谱历史、试验记录、巡检与运行信息；
  - 检索层：规程条款、检修案例、设备资料；
  - LLM 层：根因解释、证据组织、处置建议；
  - 输出层：根因类别、依据、风险提示和人工复核标记。
- 可直接引用其“多源信息 + LLM + 历史案例检索”的系统设计，说明本项目不是单次问答，而是有证据链的诊断流程。

### 局限与引用边界

- 高度依赖监控系统能发现事故，以及团队预先存在对应的 incident handler；
- 没有 handler 或监控未触发的事故，系统覆盖能力会受限；
- 验证只来自 Microsoft 的邮件服务，不能直接外推到电力设备；
- 论文主要解决根因类别预测和解释，不解决高压设备处置动作的安全合规问题；
- 因此适合作为“工程化 RCA 流水线”的参考，不应把其准确率或根因分类框架直接搬到 DGA 领域。

### 一句话结论

**C4 的价值在于证明：工业 RCA 应采用“预定义诊断流程 + 多源证据采集 + 历史案例检索 + LLM 推理解释”的组合系统；LLM 是流程中的认知组件，而不是替代规程和人工决策的黑盒。**
