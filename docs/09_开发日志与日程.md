## 四、Git 提交与推送约定（团队规范，2026-09-10 定）

**总原则：本地小步提交，远程按段推送。** 提交是为了能回滚，推送是为了备份与协作——不必一点进度就 push。

| 动作 | 频率 | 说明 |
|---|---|---|
| `git commit`（本地） | 完成一个**可描述的小成果**就提交（约 0.5–1 小时粒度） | 如"脚本跑通""文档定稿""一批规则录入完成"；这是存档点 |
| `git push`（远程） | **每天 1–2 次**（中午/收工）或里程碑前 | 多人协作时当天必须推，避免冲突 |

**提交消息规范**（前缀 + 一句话说明）：
- `feat:` 新功能（例：`feat: 新增 DeepSeek 调用 demo`）
- `fix:` 修 bug（例：`fix: 规则匹配字段名不匹配`）
- `docs:` 文档（例：`docs: 更新开发日志`）
- `chore:` 杂务（例：`chore: 调整 .gitignore`）
- `data:` 数据/规则库（例：`data: 录入 DL/T 722 表6编码`）

**其他约定**：
1. 一提交一主题：不要把文档 + 代码 + 数据混在一个提交里；
2. 开工先 `git pull --rebase`，收工 `git push`；不 push 也要先本地 `commit`（别把改动一直裸放着）；
3. **禁止提交**：`.env`/密钥、`venv/`、标准与论文 PDF（版权+体积）、大体积数据（已在 `.gitignore` 排除）；
4. 分工：**开发日志写"为什么/卡点/下一步"，提交记录写"改了什么"**，两者互补，不靠高频 push 体现进度。

**常用命令**：
```powershell
git status                 # 看改了哪些文件
git add -A                 # 暂存全部改动
git commit -m "feat: ..."  # 本地提交
git pull --rebase          # 开工/推送前先同步
git push                   # 收工推到 GitHub
```
