## 第一条：TSC：机制原理与基本流程定位

### 一、原始观点

预先运行一条或多条 TSC 采样轨迹，在结束阶段让 LLM 对多个候选结果进行聚合，以缓解单次生成输出不稳定的问题。

### 二、专业化表述

面向开放式根因分析任务，可先通过相对稳定的主轨迹完成证据收集；当流程进入结论生成阶段后，再采样一条或多条候选推理轨迹，形成多个候选诊断结果。最后，由 LLM 对候选根因链、证据和处置建议进行聚合，以降低单次生成带来的随机性和输出波动。

该思路对应 RCAgent 中的 **Trajectory-level Self-Consistency（TSC，轨迹级自洽性）**。TSC 不会让多个 Agent 从零开始完整排查，而是共享前序探索过程，仅在进入 finalization 阶段后生成多个候选结局，再对其进行聚合。

### 三、解决的问题

1. **单次生成不稳定**：同一问题多次生成时，根因表述、证据选择或处置建议可能存在差异。
2. **完整轨迹重复采样成本过高**：若从 ReAct 第一步开始重复采样，会反复调用工具和专家 Agent，增加延迟与算力消耗。
3. **随机采样容易产生无效动作**：缺少稳定历史时，Agent 更容易调用不存在的工具、重复查询或过早结束。
4. **开放式结论难以直接多数投票**：根因和处置建议通常不是单一选项，需要 LLM 对多个候选结果进行语义层面的综合。

需要区分两种聚合方式：

- **Embedding vote**：选择最接近候选语义中心的文本。
- **LLM aggregate**：让 LLM 汇总候选内容，处理共识、冲突和补充信息，并保持输出形式相对一致。

论文实验中，LLM 聚合总体优于 embedding vote。

### 四、基本流程

```text
输入故障现象与结构化数据
        |
        v
主 Agent 完成稳定的证据收集与规则调用
        |
        v
进入结论生成 / finalize 阶段
        |
        v
采样一条或多条 TSC 候选轨迹
        |
        v
获得多个候选根因、证据与处置建议
        |
        v
LLM 聚合候选结果，保留共识与有效补充
        |
        v
确定性规则校验与证据匹配
        |
        v
输出报告 / 低置信度时拒答或转人工复核
```

### 五、能否作为基本流程之一

**可以，但应定位为“条件触发的稳定性增强步骤”，而不是对所有请求无条件执行的核心步骤。**

适合作为基本流程的前提：

- 主要用于结论生成阶段，不重复执行昂贵的前序证据收集。
- 应采样多个候选，通常至少 2 个；只有 1 条轨迹无法形成自洽性。论文实验默认使用 10 个样本，并在约 20 个样本后观察到收益趋缓。
- LLM 聚合应处理多个候选的共识、冲突和补充信息，而不是简单拼接。
- 每个候选结论必须绑定可核验的证据；聚合不得新增没有原文支撑的事实。
- 最终必须经过规则引擎和证据校验，LLM 聚合不能替代 DL/T 722、DL/T 572、GB 26860 等确定性约束。
- 对停电、带电作业、停电范围和设备退出运行等高风险建议，规则校验器应拥有否决权，人工复核仍是必要关口。
- 若延迟和成本受限，可在以下条件之一满足时触发 TSC：
  - 主结论置信度较低；
  - 多个证据之间存在冲突；
  - 候选根因不唯一；
  - 处置建议涉及高风险操作；
  - 首次输出未通过 schema、引用或规则校验。

推荐将其写为本项目的基本流程组件：

**规则检索与证据收集 → 主结论生成 → 不确定时触发 TSC → LLM 聚合 → 规则/证据校验 → 人工复核。**

也可以表述为：

**证据收集与规则检索 → 主结论生成 → 低置信度/证据冲突/高风险时触发 TSC → LLM 聚合 → 规则与证据校验 → 输出或人工复核。**

### 六、项目迁移时的边界

- TSC 降低的是 LLM 的随机波动，不保证事实正确，也不保证处置建议合规。
- LLM 聚合适合整合语义和候选方案，不适合裁决安全规则。
- 多个候选一致不代表正确；候选一致但仍违反规程时，应由规则引擎否决。
- 需要记录候选数量、聚合策略、证据覆盖率和是否触发人工复核，便于后续评测。
- 原型阶段可先采用较小采样数并结合超时约束；正式实验再比较采样数量、LLM 聚合与 embedding vote 的收益和成本。
- 落地到变压器诊断时，最终仍须经过规程规则、证据匹配和人工复核。

### 七、待验证问题

1. 在本项目 30 秒响应目标下，TSC 应采样多少条候选轨迹？
2. 何时触发 TSC 最合适：首次生成后、证据冲突后，还是 finalize 前？
3. LLM 聚合是否会遗漏少数但关键的安全证据？
4. 如何设计规则引擎的否决优先级，使 LLM 聚合结果不能越过规程边界？
5. 采样数量增加带来的准确率提升，是否足以覆盖额外延迟和调用成本？

## 第二条：C2 RCAgent 其余核心机制复述

> 说明：本节根据阅读者口述整理，保留“档案柜、标准表格、项目经理、总工”等便于理解的类比。TSC 的通用原理与项目边界已合并至第一条；本节只保留 C2 其他机制，并在整体架构中用交叉引用说明 TSC 的位置。

### 一、Prompt：给 AI 的工作说明书

**通俗理解：** Prompt 就是你对 AI 说的话，说得越清楚，它越容易把任务做对。

**论文机制：** RCAgent 给 Controller Agent 注入三类基本提示：

1. **框架规则**：规定 thought–action–observation 循环、可调用工具、JSON 格式、流程和停止条件；
2. **任务要求**：明确 RCA 目标，例如找根因、生成解决方案、给出证据和判断责任；
3. **工具文档**：说明每个工具能做什么、输入什么、返回什么。

因此，Prompt 不只是“问题描述”，更是 Controller Agent 的工作说明书和权限边界。Controller 可以在给定范围内自主规划，但不能越过框架规则和任务要求自由发挥。

### 二、OBSK：桌上只放目录卡片，资料锁进档案柜

**通俗理解：** 长上下文场景下，不要把完整日志、代码或查询结果全塞给 AI。只给它头部观察和编号，把完整内容存进带编号的档案柜，需要时再用 hash ID 调回。

**论文机制：** 这对应 **Observation Snapshot Key（OBSK）**：

```text
工具返回长观察
    -> 完整 observation 存入 key-value store
    -> 给 Controller Agent：observation head + snapshot key
    -> 后续 action 引用 snapshot key
    -> 系统从档案柜取回对应原文
    -> 在受控长度下继续推理
```

**准确性校正：** OBSK 给 Controller 的主要是 **observation head（观察头部）**，不是由 LLM 生成的语义摘要。它的价值在于保留原始内容与可回取路径，避免“直接截断丢证据”或“摘要后改变原意”。

### 三、JSON 动作、JsonRegen、错误反馈与贪心解码

**通俗理解：** 如果 AI 填标准表格失败，系统让它重填、检查错误并把具体问题反馈给它，同时用较保守的贪心解码提高稳定性。

这个方向正确，但论文中其实是四种不同机制：

| 口述中的说法 | 论文中的对应机制 | 作用 |
|---|---|---|
| 所有 action 用“标准表格”填写 | JSON action | Controller 与环境使用机器可解析的 JSON 交互 |
| 表格填坏了让 AI 重填 | JsonRegen | 先清理敏感字符；失败时转成 YAML，再重生成 JSON，直到可解析 |
| 拿错误清单检查并反馈 | Error Handling | 识别重复调用、无意义专家输入、过早 finalize，并把错误原因与建议返回 Controller |
| 用保守的贪心方式写答案 | Greedy Decoding | 默认使用贪心解码，提高可复现性和动作稳定性；随机采样只用于 SC/TSC |
| 显式收工 | `finalize` 工具 | 允许 Controller 自主判断何时停止调查并提交结构化结果 |

需要校正的是：**JsonRegen 负责格式修复，Error Handling 负责行为纠错，Greedy Decoding 负责降低生成随机性。** 三者可以共同提高稳定性，但并不是“格式填错后强制用贪心重填”这一条单一规则。

### 四、Controller Agent 与 Expert Agent：项目经理和工具人

可以把 RCAgent 类比成一家排障公司：

- **Controller Agent = 唯一有决策权的项目经理**：负责规划、选择工具、读取 observation、继续推理，并决定何时调用 `finalize` 收工。
- **Expert Agent = LLM 驱动的分析工具人**：只执行代码分析或日志分析等专业任务，将分析结果作为 observation 返回，不拥有全局决策权。

| 角色 | 核心职责 | 是否有自主决策权 |
|---|---|---|
| Controller Agent | 规划、选工具、整合观察、继续推理、决定结束、汇总报告 | 有，但受 Prompt 和工具边界约束 |
| Code Expert | 递归读取代码文件、分析调用关系、提出后续读取建议、汇总代码分析 | 只完成被调用的专项分析 |
| Log Expert | 对日志分块、检索与生成分析、要求引用原文、过滤无法匹配的证据 | 只完成被调用的日志分析 |

所有角色之间的 action 使用 JSON 表单交互，`finalize` 是显式的收工铃。为了节省上下文，RCAgent 相比原始 ReAct 去掉了 few-shot action 示例。

### 五、Controller 的权限边界：不是自由人

Controller 只能在两套约束内自主决策：

1. **公司章程——框架规则**
   - thought–action–observation 循环；
   - 工具清单及调用方式；
   - JSON 数据格式；
   - 标准处理流程；
   - 停止条件与 `finalize`。

2. **业务任务书——RCA 任务要求**
   - 查找根因；
   - 生成解决方案；
   - 提供证据；
   - 判断责任归属。

因此，RCAgent 的自主性不是“想做什么就做什么”，而是 **在两个约束集合内部进行自主规划、工具选择与证据推理**。这与本项目“LLM 负责组织与解释，但必须受规程和规则约束”的设计口径一致。

### 六、TSC 在整体架构中的位置

TSC 是 RCAgent 的结束阶段质量稳定机制：复用稳定主轨迹，在 finalization 阶段采样多个候选结局，再由 LLM 聚合。详细原理、采样数量、基本流程定位和项目边界见第一条，本节不再重复。

### 七、一句话总结

RCAgent 以 Prompt 划定 Controller 的权限边界，以 Expert Agent 扩展专业分析能力，以 OBSK 管理长上下文，以 JSON/JsonRegen/Error Handling/Greedy Decoding 稳定交互，再以 TSC 在结束阶段生成多份候选结论并由 LLM 聚合，从而降低单次输出的随机波动。

### 八、需要特别注意的四点

1. OBSK 保存完整观察并只展示 **观察头部 + hash ID**，不等于生成式摘要。
2. JSON 修复、错误处理和贪心解码是不同层面的稳定化机制，不应合并成同一步骤。
3. TSC 复用前序探索过程，只在结束阶段采样候选结局；它不是多个 Agent 从零独立排查。
4. LLM 聚合形成的是候选共识，不等于安全正确性；落地到变压器诊断时，最终仍须经过规程规则、证据匹配和人工复核。
