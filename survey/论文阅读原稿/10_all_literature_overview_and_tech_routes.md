## 0. 总体判断

现有文献可以归纳成一条清晰演进链：

```text
规则/机理诊断
  -> 机器学习与深度学习
  -> 单轮 LLM / Prompt
  -> 向量 RAG
  -> GraphRAG / KG 增强
  -> Agentic RAG / 工具增强 Agent
  -> 规则约束 + RAG + Agent + 人工复核的工业混合系统
```

对本项目最重要的四个结论是：

1. **纯 LLM 不足以做工业故障诊断**：它适合语言组织、证据归纳和交互，但事实性、可追溯性和安全边界不足。
2. **向量 RAG 是最可行的基础路线**：能快速接入规程和案例，但检索相似不等于理解设备、故障和条文之间的结构关系。
3. **KG/GraphRAG 能补关系推理**：适合表达“设备—部件—现象—气体—故障—处置”的多跳关系，但建图成本高，适合作为增强项。
4. **工业落地必须混合**：确定性规则提供安全边界，RAG 提供条文和案例证据，Agent 负责多步调查，LLM 负责解释，人工负责最终复核。

对应 `docs/03` 的推荐主线：

> **规则/机理判据（路线 2-1）+ 向量 RAG（路线 1-2）+ Agentic RAG（路线 3-2）+ 规则与人工复核（路线 3-3）**
>
> 轻量 KG/GraphRAG（路线 1-3）作为加分项；领域微调（路线 1-4）因算力和可追溯性约束不作为主线。

## 1. 技术路线词典

以下编号严格沿用 `docs/03_tech_route_survey.md`。

| 编号 | 路线 | 本项目中的含义 |
|---|---|---|
| 1-1 | Prompt / 长上下文 | 直接把少量规程塞给 LLM，作为基线或简单问答 |
| 1-2 | 向量 RAG | 文档切块、Embedding、向量库 Top-k、LLM 带引用生成 |
| 1-3 | KG / GraphRAG | 构建实体关系图，支持多跳、关系约束和社区摘要 |

| 2-4 | 混合路线 | 规则约束 + RAG/TAG + LLM 生成与解释 |
| 3-1 | 单轮问答 | 一次输入、一次回答，交互深度有限 |
| 3-2 | Agent 多步工作流 | thought-action-observation 循环，动态查规则、数据和案例 |
| 3-3 | 人机协同 / 人工复核 | 高风险结论和处置建议由人确认 |

## 2. A 组：综述与全景

### A1：Large Language Models for PHM: A Review of Optimization Techniques and Applications

- **内容大概**：综述 LLM 在 PHM 中的部署优化和应用。重点包括量化、加速、PEFT（Adapter/Prompt/Prefix/LoRA）、多模态扩展，以及异常检测、故障诊断和问答。
- **核心逻辑**：工业部署的关键不只是模型能力，还有推理成本、资源约束和领域适配；PEFT 和量化是让大模型进入边缘/工业现场的手段。
- **技术路线**：1-4、2-2、2-3、3-1。
- **本项目用途**：说明 API 原型之外还存在本地化、量化和轻量微调路线，但本项目受 GPU 约束，不把微调作为主线。

### A2：Can Large Language Models Diagnose Machine Faults? A Comprehensive Survey from Deep Learning to Foundation Models

- **内容大概**：从传统数据驱动、深度学习、迁移/元学习一路梳理到 LLM 和基础模型；覆盖信号级特征、监督/自监督架构，以及 Prompt、RAG、微调式诊断流程。
- **核心逻辑**：故障诊断不是单一模型问题，而是“信号处理 + 表示学习 + 领域知识 + 推理输出”的组合；LLM 主要改变知识接入、少样本泛化和多模态融合方式。
- **技术路线**：1-1、1-2、1-4、2-2、2-3。
- **本项目用途**：用于综述“从深度学习到 LLM 的范式演进”，明确本项目选择 RAG/规则而非重训练模型的原因。

### A3：Fault Diagnosis: From Machine Learning to LLM Fusion

- **内容大概**：综述机器学习、数字孪生、知识图谱和 LLM 在故障诊断中的融合，建立多维比较框架，讨论数据质量、泛化、知识复用和物理—虚拟融合。
- **核心逻辑**：单一数据驱动方法难以覆盖复杂工业系统，未来方向是数据、知识、物理模型和语言模型协同。
- **技术路线**：1-3、1-4、2-2、2-4。
- **本项目用途**：支撑“规则/机理 + 数据 + LLM”的混合诊断架构，强调专家知识与数据驱动互补。

### A4：Foundation Models for Prognostics and Health Management: A Survey

- **内容大概**：面向工业信息物理系统，梳理Transformer、基础模型、工业知识、故障诊断、故障预测和剩余寿命预测；覆盖数据不平衡、噪声、多点关联等场景。
- **核心逻辑**：基础模型的价值在于跨任务泛化和知识迁移，但工业数据规模、标注质量、可解释性、鲁棒性和算力仍是瓶颈。
- **技术路线**：1-3、1-4、2-2、2-3。
- **本项目用途**：为“工业大模型”章节提供全景，但不足以直接支撑变压器的规程约束需求。

### A5：PHM Large Model: Outline and Progressive Paradigms

- **内容大概**：提出 PHM-LM 的概念和三个渐进范式，给出构建、应用和验证的技术路径，讨论泛化、生成、解释和验证瓶颈。
- **核心逻辑**：PHM 应从定制模型走向通用模型、从判别式走向生成式，但仍需围绕设备知识和任务验证构建系统。
- **技术路线**：1-4、2-2、2-3。
- **本项目用途**：用于展望，不作为核心实现路线；可作为“从专用模型到通用模型”的背景引用。

### A6：Large Language Models in Power Systems: A Review

- **内容大概**：综述 LLM 在电力系统管理与优化中的应用，回顾从规则到深度学习再到 Transformer 的演进，强调可解释性、可扩展性和适应性。
- **核心逻辑**：LLM 能处理复杂文本和决策支持，但电力系统要求可靠、可解释和可扩展，不能把通用模型直接当控制器。
- **技术路线**：1-1、1-4、2-1、2-3。
- **本项目用途**：支撑电力领域“LLM 是辅助决策工具，不是直接执行机构”的边界论述。

### A7：人工智能大模型在电力设备运维场景中的应用探讨

- **内容大概**：覆盖健康评估、状态预测、故障诊断、寿命预测和检修策略推荐；提出知识图谱检索增强、多模态对齐、微调和持续学习，并讨论数据质量、黑箱、环境变化导致的性能衰退。
- **核心逻辑**：电力设备运维需要多模态大模型与知识工程结合，但必须持续监控数据质量和模型反馈。
- **技术路线**：1-2、1-3、1-4、2-4、3-3。
- **本项目用途**：与本项目最接近的中文电力设备运维综述之一，可直接支撑多模态、RAG、KG 和人工复核的研究背景。

## 3. B 组：RAG、KG 与知识增强

### B0：Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks

- **内容大概**：RAG 奠基论文，把预训练生成模型与可微检索器结合，以 Wikipedia 稠密向量索引作为非参数记忆；比较 RAG-Sequence 和 RAG-Token。
- **核心逻辑**：参数记忆负责语言生成，非参数记忆负责事实知识；外部检索改善知识密集型任务并提供来源更新的可能。
- **技术路线**：1-2。
- **本项目用途**：RAG 综述中的理论起点，用于说明“外部知识库 + LLM”是解决知识陈旧和事实来源问题的基本范式。

### B1：Retrieval-Augmented Generation for Large Language Models: A Survey

- **内容大概**：将 RAG 分为 Naive、Advanced、Modular 三阶段，覆盖数据切分、索引、查询优化、混合检索、重排序、上下文压缩和自适应检索。
- **核心逻辑**：RAG 的效果由检索和增强过程共同决定，单纯增加 Top-k 不能保证事实性；检索前后处理决定质量上限。
- **技术路线**：1-2、2-4。
- **本项目用途**：本项目 RAG 模块的总分类骨架；明确采用“混合检索/重排/引用生成”的 Advanced RAG 方向。

### B2：Graph Retrieval-Augmented Generation: A Survey

- **内容大概**：系统综述 GraphRAG 的图索引、图引导检索和图增强生成，覆盖训练方式、下游任务、应用和评测。
- **核心逻辑**：图结构能保留实体、关系和路径信息，弥补向量 RAG 在全局和多跳问题上的不足。
- **技术路线**：1-3。
- **本项目用途**：作为“特征气体—故障类型—部件—处置”知识图谱的可选理论依据。

### B2a：From Local to Global: A Graph RAG Approach to Query-Focused Summarization

- **内容大概**：用 LLM 从文本构建知识图，做社区检测与社区摘要，再通过 map-reduce 支持全局查询和局部查询。
- **核心逻辑**：普通向量 RAG 擅长定位具体片段，但不擅长回答整个语料的全局主题问题；GraphRAG 用图社区摘要补足全局推理。
- **技术路线**：1-3。
- **本项目用途**：若需要回答“哪些故障模式共同涉及某类部件/气体”等跨文档问题，可作为轻量图谱的参考。

### B3：Unifying Large Language Models and Knowledge Graphs: A Roadmap

- **内容大概**：将 LLM+KG 分为 KG-enhanced LLMs、LLM-augmented KGs 和 Synergized LLMs+KGs 三条路线，覆盖预训练、推理、可解释性、补全、构建和协同。
- **核心逻辑**：LLM 擅长文本和泛化，KG 擅长显式结构和事实约束，两者应互补而非互相替代。
- **技术路线**：1-3、1-4。
- **本项目用途**：为“知识图谱增强 LLM”和“LLM 辅助知识抽取”提供统一分类，适合在综述中作为图谱路线总纲。

### B4：Can Knowledge Graphs Reduce Hallucinations in LLMs? A Survey

- **内容大概**：将知识图谱防幻觉方法分为知识感知推理、知识感知训练和知识感知验证；前者包括 KG 检索、KG 推理和知识控制生成。
- **核心逻辑**：幻觉根因之一是参数知识不足或冲突，结构化外部知识可以在检索、推理和验证三个层面增加事实约束。
- **技术路线**：1-3。
- **本项目用途**：支撑“规则/KG 约束 LLM”而非只靠 Prompt 说服模型的防幻觉论证。

### B5：From Vectors to Knowledge Graphs: A Comprehensive Analysis of Modern RAG Architectures

- **内容大概**：提出索引、检索、融合、生成四阶段统一分类，比较 Vector RAG、Graph RAG、Agentic RAG、Multimodal RAG 和 Hybrid RAG，并比较向量库与图数据库。
- **核心逻辑**：现代 RAG 不是单一拓扑，而是可以按数据形态、关系需求、推理步数和模态组合选择的架构族。
- **技术路线**：1-2、1-3、3-2。
- **本项目用途**：写“向量 vs 图谱 vs Agentic RAG”对比表和解释本项目为何选择 Hybrid 路线的主要依据。

### B6：How Can the Integration of AI Large Language Models and Knowledge Graph Enhance Fault Diagnosis?

- **内容大概**：系统综述 LLM+KG 在工业故障诊断中的应用，覆盖本体、知识抽取、GraphRAG 索引/检索/生成、评测和工业场景差异。
- **核心逻辑**：KG 提供结构和关系，LLM 提供自然语言理解与生成；二者结合能把诊断知识从“相似文本检索”提升到“关系与因果检索”。
- **技术路线**：1-3、2-4。
- **本项目用途**：最贴近“知识图谱 + LLM 故障诊断”的系统综述，可作为本项目图谱增强路线的核心综述引用。

## 4. C 组：RCA、AIOps 与 Agent

### C1：A Survey of AIOps in the Era of Large Language Models

- **内容大概**：按数据、任务、方法、评测四个研究问题综述 LLM4AIOps；AIOps 流程为故障感知、根因分析、辅助处置。
- **核心逻辑**：LLM 扩展了可用数据源和任务形态，但时延、成本、泛化、工具链集成仍是关键约束。
- **技术路线**：1-1、1-2、1-4、2-1、2-3、2-4、3-2。
- **本项目用途**：提供任务分类和评测框架；明确本项目属于“根因分析 + 辅助处置”，不是自动执行系统。

### C2：RCAgent: Cloud Root Cause Analysis by Autonomous Agents with Tool-Augmented LLMs

- **内容大概**：面向真实工业云 RCA 的工具增强 Agent。Controller Agent 负责规划，Expert Agent 负责代码/日志分析；通过 OBSK、JsonRegen、错误反馈和 TSC 提升稳定性。
- **核心逻辑**：让 Agent 自主决定“下一步查什么”，比一次性分析静态文本更接近真实排障；但需要工具、schema、上下文管理和多候选聚合。
- **技术路线**：1-1、1-2、2-4、3-2。
- **本项目用途**：Agent 工作流和规范化报告的直接对标。可迁移“控制 Agent + 专用工具 + 证据链 + 稳定化 + 人工复核”。

### C3：Exploring LLM-based Agents for Root Cause Analysis

- **内容大概**：用 ReAct + LangChain 在云事故数据上做实证评估，比较检索、CoT、IR-CoT，并开展专用工具接入案例。
- **核心逻辑**：ReAct 的事实性有价值，但静态事故文本中的讨论评论没有显著提升效果；专用诊断工具和可交互环境比单纯增加文本更重要。
- **技术路线**：1-2、2-3、3-2。
- **本项目用途**：作为“仅有案例 RAG 不够，必须提供计算/查询工具”的实证依据；方法创新有限，不宜作为核心方法对标。

### C4：Automatic Root Cause Analysis via Large Language Models for Cloud Incidents（RCACopilot）

- **内容大概**：按告警类型匹配 OCE 预定义 handler，采集日志/指标/链路等多源信息，经 LLM 总结、历史事故检索和 CoT 预测根因类别；Micro-F1 0.766。
- **核心逻辑**：确定性 handler 决定“查什么、从哪里查”，LLM 负责总结、关联和解释；系统不是让 LLM 自由探索。
- **技术路线**：1-2、2-4、3-2。
- **本项目用途**：借鉴“handler 思维”为本项目预设 DGA 异常调查路径，最符合高安全工业场景。

### C5：DiagAgent: Power Equipment Fault Diagnosis via RAG + MCP

- **内容大概**：构建设备信息和历史案例知识库，采用多层次混合检索；LLM 通过 MCP 动态调用运行数据、SF6 压力和仿真等专用小模型工具，输出结构化诊断报告；套管案例准确率 91.3%。
- **核心逻辑**：RAG 负责知识，专用小模型负责数值和领域分析，MCP/工具调用负责把二者编排起来。
- **技术路线**：1-2、2-4、3-2。
- **本项目用途**：与任务三最接近的电力设备 Agent 参考；可对应 DGA 计算器、规程检索器、案例检索器和报告生成器。

### C6：FaultSeer: Agentic RAG for Defect Analysis in Power Systems

- **内容大概**：基于 DeepSeek V3、本地知识库、Embedding 检索和重排序分析电力缺陷，支持按厂家、时间、地区进行多维度查询和统计，并用语义归一化与模糊匹配处理不一致记录。
- **核心逻辑**：本地知识库 + 重排序 + 数据规范化可缓解电力缺陷描述差异和模糊查询问题。
- **技术路线**：1-2、2-4、3-1。
- **本项目用途**：可参考其数据规范化和重排序设计，但其“Agentic”主要体现在检索工作流，交互自主性弱于 C2/C5。

## 5. D 组：电力设备与变压器专项应用

### D1：LLM-Assisted Fault Diagnosis Framework for Power Equipment

- **内容大概**：融合 DGA、局放、红外、振动和告警等多源监测数据；数值模型输出故障概率，LLM 在知识约束下组织证据和推理，引入置信度融合与一致性检查。
- **核心逻辑**：LLM 不直接替代数值模型，而是接收结构化证据并做可解释的融合解释。
- **技术路线**：2-1、2-2、2-4、3-2。
- **本项目用途**：可直接映射为“规则引擎输出候选故障 + LLM 组织根因链 + 一致性检查”的架构。

### D2：Multimodal Retrieval-Augmented Diagnosis for Oil-Immersed Transformers

- **内容大概**：融合 DGA、红外、声学和人工巡检文本，构造结构化 Prompt，从本地维护知识库检索，在便携终端生成诊断结论和维护计划；在 1000 条巡检数据上报告 97.1% 准确率、BLEU-4 72.4。
- **核心逻辑**：单一 DGA 只能反映部分故障信息，多模态融合和本地 RAG 可提高解释性与现场可用性。
- **技术路线**：1-2、2-2、2-4、3-1。
- **本项目用途**：最接近“油浸式变压器 + RAG + 多模态”的工程参考。可借鉴多模态证据融合，但本项目仍以 DGA 为主线。

### D4：CausalKGPT: Industrial Causal Knowledge-Enhanced LLM for Cause Analysis

- **内容大概**：面向航空产品制造质量问题，估计和强化质量知识之间的因果关系，再把因果知识用于 LLM Prompt，做原因分析。
- **核心逻辑**：相似性检索不等于因果关系；显式因果知识可以约束 LLM 的原因推测路径。
- **技术路线**：1-3、2-4、3-1。
- **本项目用途**：为“气体—故障—部件—处置”的因果链建模提供方法参考；若做轻量 KG，可优先保留因果边而不是任意关系边。

### D5：GAT-RAG for Wind Power Equipment Maintenance

- **内容大概**：构建融合文本、图像和结构化数据的知识图谱，用 GAT 学习实体间的语义依赖和上下文关系，在 RAG 中做结构感知检索，生成风电设备维护建议。
- **核心逻辑**：图注意力能增强复杂语义环境下的上下文建模和多跳语义连接，改善维护建议的逻辑连贯性。
- **技术路线**：1-3、2-4、3-2。
- **本项目用途**：跨行业验证“KG + GAT + RAG”对维护建议生成的有效性，可作为图谱增强的加分项参考。

### D6：基于大语言模型的图检索增强生成技术在核电领域的应用与展望

- **内容大概**：讨论 LLM 与知识图谱结合、尤其是 GRAG 在核电风险评估、智能问答、知识管理、故障诊断和预测中的应用，给出微调、领域 KG 构建和 GRAG 增强路径。
- **核心逻辑**：专业领域需要把领域图谱作为外部结构约束，以缓解知识局限、幻觉和高推理成本。
- **技术路线**：1-3、1-4、2-4、3-3。
- **本项目用途**：中文同构高安全领域的 GRAG 综述，适合引用“专业领域为什么需要图谱与人工可控性”。

## 6. E 组：DGA 领域方法与评测底座

### E0：Interpretation of Gas-In-Oil Analysis Using IEC 60599 and IEC TC10 Databases

- **内容大概**：介绍 IEC 60599 的故障分类、气体比值和正常/报警浓度，并公开用于修订标准的故障与正常样本数据库。
- **核心逻辑**：DGA 可通过故障类型和气体比例建立规则映射，历史数据库可作为规则验证和评测来源。
- **技术路线**：2-1。
- **本项目用途**：作为 DGA 数据来源和故障类型背景；但正式诊断口径仍以 DL/T 722-2014 为准。

### E2：Conventional Dissolved Gases Analysis in Power Transformers: Review

- **内容大概**：综述 Key Gas、Dornenburg、Rogers、IEC ratio、Duval Triangle、Duval Pentagon、Three Rates 和 Heptagon 等方法，并在 IEC TC10 数据上比较。
- **核心逻辑**：不同 DGA 判据有各自敏感故障类型和盲区，没有单一步骤能覆盖全部故障，组合判据更可靠。
- **技术路线**：2-1、2-2。
- **本项目用途**：用于解释为什么规则层不能只有一个三比值；本项目以 DL/T 722 为主线，同时保留注意值和产气速率校验。

### E3：Traditional Fault Diagnosis Methods for Mineral Oil-Immersed Power Transformers Based on DGA

- **内容大概**：系统回顾传统 DGA 方法，包括特征气体、比值法、图形法和组合方法，并比较 AI 方法的精度与可复现性。
- **核心逻辑**：传统方法简单、透明、可复核；AI 方法可能更准确，但常缺少可复现性和机理解释。
- **技术路线**：2-1、2-2。
- **本项目用途**：支撑“采用传统判据做确定性底座，LLM 不直接替代 DGA 规则”的路线选择。

## 7. F 组：幻觉抑制、纠错与可溯源

### F1：ReAct: Synergizing Reasoning and Acting in Language Models

- **内容大概**：让 LLM 交替生成推理和行动，通过工具或环境获取信息，再根据 observation 继续推理。
- **核心逻辑**：外部行动能为推理提供新事实，减少纯 CoT 的错误传播，并提升可解释性。
- **技术路线**：3-2。
- **本项目用途**：Agent 工作流基座。对应“思考需要什么证据 → 调工具查询 → 读取结果 → 再判断”。

### F2：Self-RAG: Learning to Retrieve, Generate and Critique through Self-Reflection

- **内容大概**：训练模型生成反思 token，自适应决定是否检索，并评价检索相关性、支持度和生成有用性。
- **核心逻辑**：不是每个问题都需要检索；检索结果也要经过自评过滤，才能避免无关上下文破坏生成。
- **技术路线**：1-2、2-4、3-2。
- **本项目用途**：可迁移为“按排查阶段触发检索”和“检索结果质量门槛”设计。

### F3：Corrective Retrieval Augmented Generation（CRAG）

- **内容大概**：用轻量检索评估器判断检索质量，对准确、模糊、错误情况采取不同纠错动作，并使用 decompose-recompose 和网络检索增强。
- **核心逻辑**：RAG 的关键风险是“检索错→生成错”，需要在生成前判断检索是否可信。
- **技术路线**：1-2、2-4。
- **本项目用途**：本项目可把“网络搜索”替换为法规库、标准库和其他可靠知识源；低置信度时扩大检索或拒答。

### F4：RARR: Researching and Revising What Language Models Say, Using Language Models

- **内容大概**：生成后先研究可验证片段并检索证据，再修订没有依据的内容，同时尽量保持原意。
- **核心逻辑**：把事实核查从“生成时尽量正确”改成“生成后逐条查证和修订”，提高归因率。
- **技术路线**：2-4、3-3。
- **本项目用途**：报告生成后的引用核查层；每条根因、证据和处置建议都应能回到规程条号或案例来源。

## 8. 标准与规则底座

### DL/T 722-2014《变压器油中溶解气体分析和判断导则》

- **内容大概**：规定油中溶解气体分析、注意值、产气速率、三比值编码和故障类型判断等。
- **核心逻辑**：将 DGA 数值转化为可复核的故障类型判据，是本项目的正式 DGA 判据来源。
- **技术路线**：2-1。
- **本项目用途**：规则引擎第一依据；表格和编码仍需按原 PDF 人工核验，未核验条目不能直接用于最终诊断。

- **技术路线**：2-1、3-3。
- **本项目用途**：为“根因分析之后能不能建议继续运行、减负荷、停电检查”提供规程依据；高风险动作必须引用条号并转人工复核。

## 9. 技术路线综合：文献支持度

### 9.1 路线 1-1：Prompt / 长上下文

- **支持文献**：A2、A6、C1、C2。
- **文献共识**：适合少量文档和快速原型，不适合大量规程、持续更新和严格溯源。
- **本项目结论**：只作为纯 LLM 对照组或降级兜底，不作为主流程。

### 9.2 路线 1-2：向量 RAG

- **支持文献**：B0、B1、B5、F2、F3、C3、C4、C5、C6、A7、D2。
- **文献共识**：免训练、更新快、可引用，是当前最成熟的领域知识接入方式；上限取决于切分、检索、重排和上下文筛选。
- **本项目结论**：必须作为 MVP 主线之一。用于检索 DL/T 722、DL/T 572、案例和检修资料。

### 9.3 路线 1-3：KG / GraphRAG

- **支持文献**：B2、B2a、B3、B4、B5、B6、A3、A7、D4、D5、D6。
- **文献共识**：能表达关系、因果和多跳路径，适合跨文档和全局问题；但建图、抽取和校验成本高。
- **本项目结论**：作为加分项。先做轻量关系图：特征气体 → 故障类型 → 可能原因 → 部件 → 处置 → 规程条号。

### 9.4 路线 1-4：领域微调 / LoRA

- **支持文献**：A1、A2、A4、A5、D6。
- **文献共识**：能改善领域术语和输出格式，但需要 GPU、标注和数据版本管理；知识写入参数后难更新、难溯源。
- **本项目结论**：不作为主线。用 Prompt/Schema/RAG 替代，并在报告中说明算力和可追溯性原因。

### 9.5 路线 2-1：规则 / 机理法

- **支持文献**：DL/T 722、DL/T 572、E0、E2、E3、D1。
- **文献共识**：可解释、可复核、稳定，是 DGA 诊断的确定性底座；缺点是覆盖面有限、边界情况可能失效。
- **本项目结论**：最高优先级。规则引擎应能独立产出故障类型、判据和置信/覆盖状态，并拥有对 LLM 建议的否决权。

### 9.6 路线 2-2：数据驱动 ML / DL

- **支持文献**：A1、A2、A3、A4、A5、E2、E3、D1、D2。
- **文献共识**：样本充足时能提升分类精度，但工业严重故障样本稀缺，黑箱模型难以满足合规解释。
- **本项目结论**：仅作为对照实验或辅助置信度，不作为主要诊断依据。

### 9.7 路线 2-3：纯 LLM

- **支持文献**：C1、C3、A2。
- **文献共识**：通用推理和表达强，但事实准确性、知识时效和可追溯性不足；在工业诊断中产生危险建议的风险高。
- **本项目结论**：只保留为基线，用来证明规则 + RAG 的必要性。

### 9.8 路线 2-4：混合路线

- **支持文献**：C2、C4、C5、C6、D1、D2、D4、D5、D6、F2、F3、F4、A7、B6。
- **文献共识**：确定性模块负责约束和数值计算，RAG 负责证据，LLM 负责解释和报告，是高风险工业场景的合理组合。
- **本项目结论**：最终主线。具体为：

```text
DL/T 722 规则引擎
  + DGA 数据校验与计算工具
  + 向量 RAG 检索规程/案例
  + Agent 多步调查
  + LLM 根因链和报告生成
  + 引用校验 + 规则复核 + 人工关口
```

### 9.9 路线 3-1：单轮问答

- **支持文献**：A1、C6、D2、D4。
- **文献共识**：实现简单，适合知识问答和单次分析，但无法完成需要多轮查证和动态工具调用的排障。
- **本项目结论**：作为最低阶交互形式，不作为任务三主流程。

### 9.10 路线 3-2：Agent 多步工作流

- **支持文献**：F1、F2、C1、C2、C3、C4、C5、D5。
- **文献共识**：Agent 能动态收集证据、调用工具并在 observation 后修订判断；但需要工具 schema、错误处理、上下文管理和稳定性控制。
- **本项目结论**：任务三主线。推荐采用“规则工具先行、RAG 按需检索、专家工具分析、最终报告”的受控 Agent。

### 9.11 路线 3-3：人机协同 / 人工复核

- **支持文献**：DL/T 572、F4、A7、D6。
- **文献共识**：高风险建议不应由模型自动执行；关键结论应提供证据并保留人工确认。
- **本项目结论**：合规底线。凡涉及停运、检修、带电作业、隔离或恢复送电的建议，必须带规程依据并标记人工复核。

## 10. 对本项目的最终选型结论

### 10.1 推荐技术栈

```text
数据层：DGA 数据 + 试验记录 + 巡检文本 + 设备资料
规则层：DL/T 722 注意值/产气速率/三比值 + DL/T 572 处置规则
检索层：Chroma 向量库 + 结构感知切分 + 元数据过滤 + 重排
增强层（可选）：特征气体—故障类型—部件—处置轻量知识图谱
编排层：受控 Agentic RAG，固定工具优先，动态检索补充
生成层：LLM 组织根因链与处置建议，强制引用原文条号
校验层：schema、引用匹配、规则否决、危险建议拦截
交互层：人工复核关口与可追溯证据面板
```

### 10.2 为什么这条路线最合适

1. 现有 DGA 方法文献证明传统判据可靠、透明，是规则底座。
2. RAG/KG 文献证明外部知识能改善事实性和可更新性，但检索错误会传播。
3. Agent 文献证明多步工具调用比单轮生成更接近真实排障，但必须有稳定化和工具约束。
4. 电力专项文献表明，工业场景更倾向于多源、混合、可解释和人工复核，而不是全自动黑箱。

### 10.3 不采用或暂不采用

- **不采用纯 LLM 作最终结论**：无法满足可溯源和安全要求。
- **不以微调为主**：GPU 和数据条件不足，知识更新困难，不利于条号级溯源。
- **不把完整 GraphRAG 作为 MVP 前置条件**：建图成本高；先用规则和向量 RAG，后续再做轻量关系图消融。
- **不把自动处置作为默认能力**：高压设备风险高，先做诊断建议和人工复核。

## 11. 一句话收束

所有文献最终指向同一个结论：

> **工业故障诊断的可信路线不是“让 LLM 知道一切”，而是让确定性知识、外部证据、专用工具和语言模型各司其职，再用可验证的流程把它们的输出约束起来。**
