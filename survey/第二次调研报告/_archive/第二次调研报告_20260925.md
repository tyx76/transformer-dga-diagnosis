## 摘要

本报告围绕油浸式电力变压器故障根因分析智能体，对行业落地路线、多模态融合、知识图谱与 GraphRAG、RAG 演进、受控 Agent、LoRA 微调、可信生成和项目当前实现进行第二轮调研。结论是：工业故障诊断不能采用纯大模型路线，较稳妥的方案应把确定性规则、外部知识、混合检索、专用工具、受控 Agent、引用校验和人工复核组合起来。

相较初次报告，本轮新增了三项判断。第一，行业案例已经形成“领域知识库 + 专用模型/工具 + 人工复核”的共同方向，但不同案例的自动化和多模态程度差异很大，不能直接横向比较效果数字。第二，RAG 的关键矛盾会随系统成熟从“找不到”转向“排不上”，项目 50 条用例的 Top-5 命中率为 76.92%，目标条文已进入单路 Top-10，说明下一阶段优化重点应是查询改写与 Reranker，而不是单纯扩大 Top-K。第三，RCAgent 提供了可迁移的受控 Agent 工程骨架：Controller Agent 负责规划，专家工具负责局部分析，OBSK 管理长观察，结构化输出与错误反馈控制动作，自洽性聚合只用于候选根因，最终安全结论仍由规则和人工复核把关。

推荐路线为：**DL/T 722 规则引擎 + DL/T 572 安全与运行边界 + BM25/向量混合检索 + RRF/Reranker + 证据库 + 受控 Agent + 引用校验 + 人工复核**。GraphRAG、多模态融合和 LoRA 分别作为第二阶段增强、后续扩展和对照实验，不作为当前 MVP 的前置条件。

**关键词：** 油浸式变压器；DGA；RAG；GraphRAG；多模态融合；RCAgent；OBSK；LoRA；可信生成；人工复核


本报告的阅读主线是：先明确任务和安全边界，再通过行业案例判断外部趋势，随后给出技术路线总体比较与选型结论；分项论证按 RAG、Agent、知识图谱、多模态和 LoRA 展开；最后落到项目现状、推荐架构、实施顺序和风险结论。

## 1. 调研背景、范围与方法

### 1.1 项目背景

油浸式电力变压器是输变电和工业厂站中的关键设备。绝缘油在热故障、放电故障和受潮等异常条件下会分解产生特征气体，油中溶解气体分析（DGA）因此成为发现早期故障、判断故障类型和指导检修的重要手段。传统诊断依赖专家翻阅规程、对照注意值、计算产气速率并完成三比值编码，过程专业性强、效率受经验影响，跨文档的证据关联也比较困难。

大语言模型能够组织规程、案例和设备数据，并生成可读的诊断报告，但工业场景不能接受无依据推断。本项目的核心问题不是让大模型自由诊断，而是用规则、证据和可验证流程约束大模型。

### 1.2 对象与边界

- 对象范围：输变电及工业厂站中的油浸式电力变压器，重点为主变。
- 诊断主线：以 DL/T 722-2014 为 DGA 判据依据，关注特征气体、注意值、产气速率、三比值编码和故障类型判断。
- 辅助证据：DL/T 572-2021 的运行、维护和异常处置条款；电气试验、巡检记录和设备历史资料作为后续扩展。
- 明确排除：干式变压器、配电/低压小变压器和纯油务理化指标不作主诊断路径。
- 合规边界：涉及继续运行、减负荷、停电检查、隔离检修和恢复送电的建议必须引用规程，保留人工复核，不由 LLM 自动执行。
- 未命中策略：知识库没有命中可支持条文时拒答或要求补充信息，不以模型常识补写结论。

### 1.3 本轮材料与方法

本轮调研使用三类材料：

1. 论文阅读笔记：`论文阅读(已自动还原).xlsx`，包含 RCAgent、OBSK、RAG 基础论文、现代 RAG 架构综述、动态图路由和 EvLink 证据链接等条目。
2. 行业技术调研：`Doc2.docx`，包含电力行业市场案例，以及多模态融合、知识图谱、GraphRAG 和 LoRA 的技术细节。
3. 项目内证据：`README.md`、`docs/00_项目管理/00_project_status.md`、`docs/00_项目管理/05_dev_log_and_schedule.md`、`docs/00_项目管理/08_acceptance_record.md`、`docs/01_调研与方案/10_all_literature_overview_and_tech_routes.md` 和现有初次报告。

对材料采用“观点—依据—适用边界—项目动作”四步整理。附件中的效果数字只作为线索，不直接升级为已核验事实；能够由仓库测试记录支持的数字单独标注为本项目实测。

## 2. 行业现状与落地路线

### 2.1 行业案例汇总

初次报告已经整理了公开行业材料，本轮行业调研补充了“行业大模型 + 多模态”“知识图谱 + RAG”“DGA 专属知识库 + 思维链”“RAG + LoRA”等路线。合并后的案例矩阵如下：

| 来源 | 场景 | 技术路线 | 团队整理指标或结论 | 对本项目的启示 |

| 国网福建电力 | 输电线路故障原因辨识 | 大小模型协同 + 多智能体 | 5 分钟识别 6 类故障；220kV 及以上事故准确率 80% 以上 | 小模型处理数值/波形，大模型负责语义推理 |

| 国家电投河南公司 | 火电机组预警诊断 | DeepSeek + RAG + 专业知识库 | 覆盖 200MW–1000MW 机组；预警准确率超过 85% | RAG 在电力设备预警中有工程价值，但需核验口径 |

### 2.2 行业技术共识

1. **专业知识库是必要条件。** 电力设备诊断依赖标准、规程、案例和设备台账，通用模型参数无法替代可更新的外部知识。
2. **模型不承担全部精确计算。** 注意值、产气速率、三比值和其他确定性计算应由规则或专用工具完成，大模型负责解释、组织和交互。
3. **高风险处置必须保留人工关口。** 行业案例通常把 AI 限定为辅助研判或建议生成，不把停送电等高风险动作交给模型自动执行。
4. **多模态能力与建设成本同步上升。** 多源数据能提高覆盖面，但会带来时间对齐、标注、权限、存储和评测问题。
5. **不同技术路线解决不同瓶颈。** RAG 解决知识更新与引用，图结构解决关系和跨文档推理，Agent 解决动态收集证据，微调解决固定任务适配，不能互相替代。

### 2.3 本项目差异化定位

本项目采取轻量、聚焦、可复现的技术路线：

- 聚焦油浸式主变 DGA，不追求全行业设备覆盖；
- 以 DL/T 722-2014 和 DL/T 572-2021 为正式依据；
- 结论必须落到具体文档和条号，未命中时拒答；
- 先跑通规则与混合检索闭环，再增加 Agent、轻量图谱和多模态；
- 处置建议保留人工复核，不直接输出自动操作指令。

本报告先给出技术路线的总体比较和选型结论，再按当前主链路、智能体增强、知识结构增强、数据模态扩展和模型微调的顺序展开分项论证，最后回到项目现状、总体架构和实施路线。

### 3.1 技术路线总体比较

| 路线 | 解决的问题 | 主要局限 | 本项目定位 | 实施阶段 |
|---|---|---|---|---|
| Prompt / 长上下文 | 快速形成回答基线 | 容量、成本和可追溯性差 | 基线与兜底 | 已完成 |

### 3.2 本项目选型结论

推荐采用**规则优先的混合 RAG + 受控 Agent**：

1. DL/T 722 和 DL/T 572 作为正式证据来源；
2. 注意值、产气速率、三比值进入确定性规则引擎；
3. BM25 与向量检索互补，RRF 或加权融合；
4. Reranker 负责最终 Top-5 精排；
5. 证据库保存完整原文并分配 `evidence_id`；
6. 受控 Agent 只调用白名单工具并输出结构化候选；
7. LLM 根据证据生成根因链、处置建议和不确定性说明；
8. 引用校验、规则否决和人工复核共同决定是否可交付。

## 4. RAG 技术路线与工程演进

### 4.1 从基础 RAG 到混合 RAG

RAG 基础论文提出把预训练模型的参数记忆与非参数外部记忆结合，用于知识密集型生成任务。本项目同样采用这一思想：DL/T 722、DL/T 572 等规程属于可更新、需要引用的外部知识，不应只依赖模型参数。

现代 RAG 综述进一步把架构族分为向量 RAG、GraphRAG、Agentic RAG、Multimodal RAG 和 Hybrid RAG。选择依据不是“哪种最新”，而是数据形态、关系复杂度、推理步数和模态需求。对本项目而言：

- 非结构化规程和案例适合向量/关键词混合检索；
- 注意值、产气速率和三比值适合确定性规则；
- 跨文档因果链在后期可考虑轻量图谱；
- Agent 用于动态决定下一步查什么；
- 多模态暂作扩展路线。

### 4.2 推荐检索链路

第二轮调研确认的检索链路如下：

```text
用户问题
  → 领域/安全过滤
  → 术语、单位和同义词规范化
  → 意图路由（DGA / 油温 / 安全 / 设备 / 案例）
  → BM25 精确召回 + 向量语义召回
  → RRF 或按分数融合
  → Reranker 精排
  → 证据去重与上下文压缩
  → 带 evidence_id 的生成
  → 条号存在性、原文匹配和目标一致性校验
  → 拒答、重写或人工复核
```

### 4.3 本轮新增的工程判断

论文阅读笔记对推理增强和图结构路由的补充，说明 RAG 的演进方向不是无限扩大上下文，而是提高“何时检索、检索什么、拿回什么证据”的控制能力。对本项目的直接要求是：

1. 查询改写不能改变数值条件、设备类型和规程术语；应先做确定性规范化，再允许有限语言改写。
2. 检索结果必须有稳定证据 ID，生成阶段不能只引用自然语言标题。
3. 检索前路由、检索后重排和引用后校验是三个不同环节，不能用同一次相似度分数替代。
4. 图路由只有在问题复杂度和关系链长度明显增加时才值得引入。
5. 评测必须同时覆盖命中、排序、引用、拒答和危险建议拦截，不能只看生成文本是否流畅。

## 5. 受控 Agent 与根因分析工作流

### 5.1 为什么需要 Agent

单轮 RAG 适合“问题→检索→回答”，但真实故障排查往往需要动态收集证据：先查看气体数值，再计算产气速率，再核对历史趋势，必要时检索电气试验或案例。ReAct 类工作流通过“推理—行动—观察”循环调用工具，能更接近专家的排障过程。

Agent 的自由度越高，动作错误、重复查询、上下文膨胀和错误传播的风险越大。因此本项目应使用受控 Agent，而不是让模型自由探索。

### 5.2 RCAgent 的可迁移机制

论文阅读笔记中的 RCAgent 面向云平台根因分析，其架构对本项目有较强的工程参考价值：

| RCAgent 机制 | 作用 | 本项目迁移方式 |
|---|---|---|
| Controller Agent + Expert Agent | 主控负责规划，专家工具负责局部分析 | 主控负责调查步骤；规则、DGA 历史和条文检索作为专家工具 |
| 语义化工具 | 不把底层 SQL/检索参数直接暴露给模型 | 提供 `get_dga_history`、`estimate_rate`、`three_ratio`、`retrieve_clause` 等稳定接口 |
| JSON Action | 约束模型输出可执行动作 | 工具调用使用固定 schema，非法动作直接拒绝 |
| OBSK | 长观察只给头部和证据 ID，完整内容存外部 | 规程全文、巡检记录和案例存证据库，prompt 只放摘要与 `evidence_id` |
| JsonRegen / 错误反馈 | 修复结构化输出，减少无效动作 | schema 校验失败时返回错误信息并有限重试 |
| TSC 自洽性聚合 | 结束阶段生成多个候选并聚合 | 只用于候选根因链排序，不能替代规则和安全否决 |
| 结构化最终报告 | 输出根因、方案、证据和责任 | 输出根因链、证据表、置信度、限制条件和人工复核标记 |

RCAgent 的精读材料显示，其价值主要来自工程约束而非“多智能体”数量：专家工具与查询工具分离，OBSK 控制长上下文，JsonRegen 和错误规则降低无效动作，TSC 在 finalize 阶段聚合并行候选。其云 RCA 任务中的指标不能直接外推到变压器场景，但“工具编排 + 结构化协议 + 证据绑定 + 稳定化”的设计可以迁移。

### 5.3 本项目 Agent 动作边界

允许 Agent 自动执行：

- 解析设备信息、采样时间和气体单位；
- 调用规则工具计算注意值、产气速率和三比值候选；
- 检索规程、案例和结构化台账；
- 组织证据，生成候选根因链和处置建议草稿；
- 标记证据缺口、冲突和需要人工确认的事项。

禁止 Agent 自动执行：

- 直接下达停电、送电、隔离、检修或恢复运行指令；
- 修改规则阈值或删除证据；
- 在没有条文支持时补写合规结论；
- 用多次采样的一致性替代规则校验；
- 将未经人工确认的建议表述为必须执行的操作命令。

### 5.4 Agent 评测项

Agent 工作流至少需要评估：工具调用合法率、无效动作率、平均轨迹长度、重复查询率、证据覆盖率、根因候选命中、结构化输出通过率、引用正确率、危险建议拦截率、平均响应时间和单次成本。与云 RCA 不同，本项目的首要指标是安全与可追溯，而不是单纯提高自动化程度。

## 6. 知识图谱、GraphRAG 与证据锚定

### 6.1 知识图谱的价值

知识图谱把设备、故障、现象、原因、处置措施及其关系显式组织为图结构，适合表达跨层级关系和多跳推理。行业材料中的典型案例沿“温度异常→接触电阻变化→安装工艺缺陷→同批次施工记录”进行四跳推理，把实时告警与非实时管理信息串联起来。纯关键词检索通常只能定位当前告警文本，不能主动追溯到施工记录。

但图谱的“可达”不等于“有证据支持”。一条关系在图上可达，只能说明存在关联，不能直接证明因果关系。若关系边没有原文证据、适用条件和来源，GraphRAG 仍可能输出看似合理但无法审计的结论。

### 6.2 传统 GraphRAG 的组成

行业材料中的 GraphRAG 主要包括：

- 实体与关系建图：设备、故障、解决方案、部件、工艺和人员/班组等；
- 图编码与检索：使用图卷积网络等方法编码局部结构，支持跨层级语义检索；
- 多跳推理：沿关系链补充非结构化文本无法直接召回的管理信息和历史记录；
- LLM 辅助：把自然语言问题翻译成图查询、从文本抽取实体关系、把结构化路径转成自然语言答案、对结果排序或摘要。

这说明 LLM 在 GraphRAG 中不一定是主推理器，也可以是查询接口、抽取器和解释器。对本项目而言，规则和证据校验仍应拥有最终否决权。

### 6.3 本轮新增的图谱研究线索

论文阅读笔记补充了两类值得关注的方向：

1. **非对称动态图路由。** 传统结构化 RAG 往往对所有问题采用固定遍历策略，而动态路由根据查询意图和复杂度选择不同深度或路径。它适合问题复杂度差异很大的系统：简单条目查询走固定路径，复杂根因问题才进入多跳推理。代价是路由规则、图结构和维护成本更高。
2. **EvLink：以段落为单元、强调来源证据链接。** 该方向试图把证据支持显式加入图结构，增强可溯源性和多跳推理。其优点是保留上下文、支持证据路径；局限是粒度可能偏粗、冗余较多、关系抽取和规模化维护成本高。

### 6.4 对项目的落地建议

本项目不建设完整 GraphRAG，而先建立“轻量证据图谱”：

| 节点/边 | 示例 |
|---|---|
| 设备与部件 | 主变、绕组、套管、分接开关、冷却系统 |
| 异常现象 | 乙炔超标、油温过高、油位异常、局部放电 |
| 特征气体 | H₂、CH₄、C₂H₂、C₂H₄、C₂H₆、CO、CO₂ |
| 故障类型 | 低能放电、高能放电、局部放电、热故障 |
| 可能原因 | 绝缘老化、接触不良、受潮、过热、机械缺陷 |
| 处置建议 | 加强监视、缩短采样周期、电气试验、停电检查、检修 |
| 证据边 | 由具体规程条号、案例或试验记录支持，并记录适用条件 |

实施顺序是：先完成条号级检索和引用校验，再把“现象—气体—故障—原因—处置—条号”整理为关系表；当跨文档查询和多跳问题稳定出现后，再考虑图数据库和动态路由。初期图谱的主要作用是组织和校验证据，不是替代 RAG。

## 7. 多模态数据与融合策略

### 7.1 可用数据模态

行业材料将变压器相关数据划分为文本、油色谱、电气量、温度、振动/声音、图像/视频和结构化台账等。多模态的目标不是把所有数据简单拼接，而是让不同证据在同一故障假设下相互校验。

对本项目而言，近期的最小闭环仍是“DGA 数值 + 规程文本 + 设备背景”；电气试验和巡检文本可以在第二阶段进入证据链。振动、声学和红外数据适合作为后续扩展，不应阻塞当前 DGA 诊断主线。

### 7.2 三类融合方法

| 融合层级 | 核心逻辑 | 行业材料中的代表方法 | 适用场景 | 主要风险 |
|---|---|---|---|---|
| 早期融合 | 在原始数据或初始特征阶段合并 | 数据字典标准化；时空对齐与张量拼接；跨模态注意力 | 模态强相关且可同步采集，如振动与电流 | 对齐困难、缺失模态敏感、工程耦合高 |
| 中期融合 | 各模态先独立提特征，再在特征或语义层交互 | 交叉注意力动态加权；拼接后共享网络精炼；逐元素/双线性交互 | 复杂诊断，需要学习模态间深层关联 | 网络复杂、标注需求大、可解释性下降 |
| 晚期融合 | 各子模型先独立给出结论，再在决策层汇总 | D-S 证据理论；投票；Stacking 元学习 | 模态相关弱，或单一模态本身有较强判别力 | 错误决策可能被加权放大，阈值难定 |

行业材料指出，知识图谱路径更适合理解为晚期融合的一种：图谱沿关系链独立推理，大模型/分类器也各自输出候选根因，最后在决策层合并。这个判断对本项目很重要，因为它说明 DGA 规则、检索证据和图谱关系不必在最开始强行融合，可以通过统一证据结构在后续汇总。

### 7.3 对项目的选择

近期采用“规则证据 + 文本证据”的晚期融合：

1. DL/T 722 规则引擎给出注意值、速率和三比值候选故障类型；
2. RAG 检索给出规程条文、案例解释和处置边界；
3. 证据组织层把两类结果统一为 `evidence_id + 来源 + 条号 + 原文片段 + 适用范围`；
4. LLM 只根据合并后的证据生成根因链和报告；
5. 冲突时优先服从规程硬规则，无法消解则保留候选并提示人工复核。

早期和中期多模态融合暂不作为 MVP 前置条件。只有当电气量、红外或振动数据形成稳定采样和历史标注后，才评估是否需要特征级融合。

## 8. LoRA 微调的定位

### 8.1 原理

LoRA（Low-Rank Adaptation）冻结预训练模型原始参数，在部分层旁注入两个小矩阵，只训练低秩增量。假设原权重矩阵为 \(W\)，更新表示为 \(W+\Delta W=W+BA\)，其中 \(A\)、\(B\) 的秩远小于原始维度。秩通常取 8、16、64 等较小值，从而减少训练参数和显存需求。

### 8.2 适用范围

LoRA 适合：

- 固定术语、固定输出格式和固定任务风格；
- 样本相对稳定、更新频率低的分类或抽取任务；
- 在不改变基础模型的前提下做轻量领域适配；
- 需要把模型部署成本控制在可接受范围的场景。

LoRA 不适合替代：

- 规程注意值、产气速率和三比值的确定性计算；
- 随时改版的规程知识；
- 条号级引用和原文证据校验；
- 高风险处置建议的合规判断。

### 8.3 对项目的结论

本项目不把 LoRA 作为主路线。若后续需要统一报告格式、术语抽取或分类，可在 RAG 和规则基线稳定后做对照实验。正式评测应比较“RAG + 提示词”与“RAG + LoRA 固定格式”在引用正确率、更新成本、响应时间和安全拦截上的差异，而不是只比较分类准确率。

### 9.1 已实现主链路

### 9.3 关键诊断结论

2026-09-22 的项目日志表明：在 50 条评测用例中，目标条文通常已经出现在向量检索和 BM25 的 Top-10 中，但没有进入最终 Top-5。召回层和融合层基本正常，主要瓶颈在排序层。扩大候选 Top-10→Top-20 只能把问题往后推，RRF 权重调整也未改变最终命中结果。因此下一阶段优先探索 Reranker 和查询改写，而不是继续盲目扩大 Top-K。

### 9.4 当前主要缺口

- DL/T 722 部分正文原则条款（如 `9.3.3`、`10.2.4`、`10.3`）尚未进入正式知识库；
- DL/T 572 页码映射不完整；
- 正式 50–100 条端到端评测和引用正确率评测尚未完全归档；
- 证据目前主要依赖条号和文本片段，稳定的 `evidence_id` 与原文匹配流程仍可加强；
- Agent 仍以检索和生成链路为主，完整状态机、工具 schema 和安全否决器尚未完全实现；
- 轻量图谱、多模态和 LoRA 均未进入 MVP 主链路。

## 10. 建议系统架构

```text
输入层
  设备信息 / DGA 数值 / 历史趋势 / 试验记录 / 巡检文本 / 用户问题
        │
        ▼
校验与规范化层
  单位 / 字段完整性 / 采样时间 / 缺失值 / 设备类型 / 安全过滤
        │
        ├───────────────┐
        ▼               ▼
确定性规则层        意图与任务路由层
  注意值               DGA / 油温 / 安全 / 设备 / 案例
  产气速率
  三比值编码
        │               │
        └───────┬───────┘
                ▼
检索层
  BM25 召回 + 向量召回 → RRF/加权融合 → Reranker → 去重压缩
                │
                ▼
证据库
  evidence_id + doc_id + 条号 + 原文 + 页码 + 适用范围
                │
                ▼
受控 Agent / LLM 层
  规划 → 工具调用 → 观察 → 候选根因 → 结构化报告
                │
                ▼
校验与安全层
  schema 校验 / 条号存在 / 原文匹配 / 规则否决 / 危险建议拦截
                │
                ▼
输出层
  根因链 / 证据清单 / 处置建议 / 风险提示 / 人工复核标记
```

架构设计原则：

- 规则与 LLM 分权：规则负责数值判据和安全否决，LLM 负责解释和组织；
- 检索与生成分离：生成不能引入检索结果之外的正式依据；
- 证据与结论绑定：每条根因和处置建议都要能回到具体证据；
- Agent 工具白名单：不允许模型直接访问底层数据库或自由构造危险操作；
- 人工复核不可删除：高风险建议只输出为“建议”，不执行实际控制。

- 根因链覆盖率；

## 12. 风险、合规与边界

1. **标准文本和表格抽取错误。** 条号、公式、单位和表格错位会直接传播到结论，必须人工抽检并保留原文映射。
2. **行业案例来源不完整。** 部分案例只有二手整理数据，正式引用前需补齐原始出处、时间、适用范围和指标定义。
3. **查询改写改变语义。** 数值、单位、设备类型和规程术语应优先用确定性规则处理，LLM 只做受限改写。
4. **RAG 排序错误。** 召回命中不等于正确排序，需通过 Reranker、分块优化和评测降低错误证据进入上下文。
5. **图谱因果被误读。** 关系可达不等于因果成立，证据边必须记录来源和适用条件。
6. **Agent 越权。** 受控 Agent 只能调用白名单工具，不允许直接执行停送电、隔离、检修等操作。
7. **自洽性不等于正确性。** 多次生成一致只能辅助候选聚合，不能替代 DL/T 722、DL/T 572、GB 26860 等规则和安全边界。
8. **数据与版权。** 标准原文、第三方数据和 API 密钥应遵守版权、许可和访问控制要求，不把敏感生产数据发送到外部服务。
9. **多模态成本。** 数据对齐、标注、存储和模型训练成本较高，必须用明确的故障覆盖收益证明其优先级。

## 13. 结论与下一步

第二轮调研的核心结论是：行业实践支持知识增强、工具协同和人工复核的组合路线；RAG 仍然是当前最成熟的工程起点；图结构和 Agent 能增强关系推理与证据收集，但必须以确定性规则和证据校验为前提。LoRA 适合固定任务适配，不适合作为规程知识更新和条号溯源的主要机制。

本项目的下一阶段不应盲目扩张技术栈，而应沿着现有主链路补齐质量和安全：

1. 用真实 DeepSeek 和 Ollama 完成 50–100 条端到端评测，形成可复现基线；
2. 优先实现 Reranker 和查询改写，验证能否把 Top-10 中的正确条文稳定提升到 Top-5；
3. 为每条证据分配 `evidence_id`，实现结论、条号、原文和适用范围的绑定；
4. 将三比值、产气速率和注意值规则正式接入主链路，并增加规则否决；
5. 定义 Agent 工具 schema、动作白名单和结构化报告；
6. 在 P0/P1 稳定后再建设轻量证据图谱、多模态和 LoRA 对照实验；
7. 保留人工复核关口，不把模型生成内容直接转成设备操作指令。

一句话收束：**本项目应采用规则提供硬边界、检索提供可追溯知识、Agent 提供受控调查、LLM 提供解释和报告、人工复核提供最终安全责任的混合架构。**
