# RAG 基线测评报告

> 测评对象：现有 `retrieve()` + `generate()` 向量检索生成基线  
> 原始数据：`model_exam/测评文本原始文本.txt`  
> 报告日期：2026-09-15

## 一、结论摘要

现有系统已经具备“检索到条文后生成带引用答案”和“证据不足时拒答”的基本能力，但还没有达到可交付的故障诊断水平。

综合评价：

- **安全性：基本合格。** 对无关问题、长文本和证据不足问题，系统大多选择拒答。
- **引用能力：部分合格。** 18 条记录中有 9 条包含引用，共出现 30 次引用标记。
- **任务完成度：不合格。** 面对数值 DGA 诊断、三比值/Duval 分析、长案例和多条件问题，系统主要停留在“找到注意值”或“资料未覆盖”，没有完成诊断闭环。
- **鲁棒性：不合格。** 长问题、没有明确出现“变压器”的输入和模糊问题容易失效。
- **当前定位：** 可以作为第一阶段 baseline，不能作为最终方案。

## 四、主要发现

### 1. 短问题和明确实体问题较稳定

输入中出现“乙炔”“220kV”“C2H2”“H2”等明确实体时，系统能够命中 `DL/T 722-2014` 表3、表4等条文，并生成引用。

典型结果：

- `乙炔超标`：命中注意值和产气速率，并明确拒绝对未覆盖的处置措施作推断。
- `C2H2 = 6.2 μL/L`：正确说明超过 220kV 及以下设备的注意值。
- 长叙述中的 `2号主变 C2H2 6.2`：能够从无关内容中抓住关键数值。

### 2. 长问题会显著失效

第 7 至第 12 条都是长文本输入，全部出现以下问题：

- 0 条引用；
- 全部触发“资料未覆盖”；
- 没有从长文本中抽取真正的诊断问题；
- 没有进行实体、工况、数值和问题意图的分离。

这说明当前流程本质上是：

```text
长文本 → 直接 embedding → 向量相似度 → 生成
```

缺少：

```text
长文本理解 → 问题提取 → 实体/数值抽取 → 查询重写 → 分步检索
```

这正是项目负责人所指出的“问题长、没有提到变压器会失效”。

### 3. 数值 DGA 问题没有进入规则引擎

第 4、5、6、13、14、15、16 条包含明确的 DGA 数值或规则分析要求，但系统主要表现为：

- 查找注意值；
- 查找部分运行规程；
- 在条文不足时拒答；
- 没有自动调用三比值、Duval 三角和产气速率规则。

因此当前系统是“找条文”，不是“做诊断”。

### 4. 知识库存在结构性缺口

从回答可以看出，当前知识库至少缺少：

- DL/T 722-2014 的 `9.3.3`、`10.2.4`、`10.3` 等原则性条文；
- 三比值、Duval 三角的自动计算能力；
- 故障案例、原因、处置和证据之间的关系；
- 维护案例和反事故措施语料；
- 对 CO/CO2 比值等派生判据的覆盖。

这些缺口直接导致系统在“故障类型”“是否停电”“下一步检测”等核心问题上无法完成回答。

### 5. 拒答策略偏保守，但用户体验不足

安全性方面，系统没有明显编造具体规程条文，也没有在证据不足时强行给出危险处置建议。

但部分拒答过于生硬，例如：

- 只输出“资料未覆盖”；
- 没有告诉用户缺少哪些输入；
- 没有给出下一步可补充的数据项；
- 没有对问题做澄清或重写。

理想行为应该是：

```text
资料未覆盖 → 指出缺少的证据 → 提出结构化追问 → 给出可执行的下一步检测项
```

## 五、当前 RAG 的主要短板

| 环节 | 当前做法 | 问题 |
|---|---|---|
| 输入理解 | 直接把整段文本 embedding | 长文本稀释关键词，缺少实体和意图 |
| 文档预处理 | 主要按条文切块 | 没有案例卡、表格层级和关系抽取 |
| 检索 | 单一向量相似度 | 缺少 BM25、Metadata Filter、混合检索和重排 |
| 规则诊断 | 规则脚本独立存在 | 没有接入问答主链路 |
| 生成 | 提示词限制 + 引用要求 | 没有生成后的引用存在性校验 |
| 评测 | 最终文本人工观察 | 没有 Top-k、分数、页码和 ground truth |
| Agent | 线性 retrieve → generate | 没有规划、验证、纠错和再检索 |

## 六、改进建议

### P0：先把测评数据变完整

每次运行至少记录：

```text
原始问题
查询改写结果
意图分类
实体和槽位
Top-k 条文
相似度分数
doc_id / clause / page
规则计算结果
最终回答
引用校验结果
```

没有这些字段，后续无法做真正的检索和诊断评测。

### P0：增加查询理解和改写

在线流程应先做：

```text
问题清洗
→ 实体抽取（设备、电压等级、气体、数值）
→ 意图判断（查标准、算规则、找案例、问处置）
→ 查询改写
→ 分步检索
```

重点解决：

- 长文本没有明确问题；
- 没有出现“变压器”但实际问的是 DGA；
- 一个输入包含多个子问题；
- 输入包含大量无关背景。

### P0：补齐 722 关键条文并接入规则引擎

至少补入：

- 注意值的应用原则；
- 产气速率和趋势判断；
- 三比值编码和故障类型映射；
- Duval 三角或等效的解释规则；
- 不同故障类型的后续检测与处置边界。

问答链路应变为：

```text
数值输入 → 规则计算 → 检索证据 → 诊断结论 → 处置边界
```

### P1：文档预处理和案例抽取

建立多类知识资产：

```text
标准条文库
判据/表格库
故障案例库
规则库
因果/关系图谱
```

故障案例应抽成结构化卡片：

```text
设备
电压等级
运行年限
气体数值
症状
故障类型
原因
处置
检测项
出处
```

### P1：混合检索和重排

推荐顺序：

```text
BM25 + 向量检索
→ Metadata Filter
→ Reranker
→ 证据去重
→ 引用约束生成
```

对于“变压器”“C2H2”“三比值”“220kV”等专业词，关键词检索应作为向量检索的补充，而不是被完全替代。

### P2：Agent 化工作流

后续目标不是单次问答，而是：

```text
理解问题
→ 判断是否需要规则
→ 检索标准和案例
→ 调用规则工具
→ 检查证据是否充分
→ 必要时补检索
→ 生成报告
→ 校验引用
→ 人工复核
```

## 七、总体评价

| 维度 | 评价 |
|---|---|
| 基本安全性 | 较好 |
| 无关问题拒答 | 较好 |
| 短问题检索 | 基本可用 |
| 长问题理解 | 不合格 |
| 数值诊断 | 不合格 |
| 规则编排 | 不合格 |
| 案例检索 | 未具备 |
| 引用完整性 | 部分合格 |
| 可评测性 | 不足 |
| 最终可交付性 | 尚未达到 |

**总体结论：** 当前版本适合作为“朴素向量 RAG 基线”和失败案例来源，不适合直接作为最终诊断系统。下一步应先重做文档预处理、查询理解、混合检索和 Agent Workflow 调研，再进入重构。
